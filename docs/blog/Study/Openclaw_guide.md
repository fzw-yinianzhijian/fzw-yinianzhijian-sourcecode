最近我在折腾本地自动化助手，踩了不少坑，也被它省了不少时间，所以决定开这个坑，写一篇我自己的 `openclaw` 使用指南。先说明，这不是官方文档翻译，也不是一步到位的“大全”，而是我按真实使用顺序整理出来的“能跑起来、能避坑、能继续长出来”的版本。今天先写第一版，先把最小闭环搭起来，后面再按场景慢慢补。

先给刚接触的同学一个直觉：`openclaw` 可以理解成一个“会用工具的本地助理框架”。它不只是聊天，而是能在权限范围内读写文件、跑命令、连浏览器、做一些自动化动作。你给它目标，它会拆步骤执行，最后把结果回给你。对初学者来说，最重要的不是一上来学全，而是先把“我发一个任务，它能在本机帮我完成”这件事跑通。

我的上手路径很朴素，基本按最小可运行走：

1. **先确认环境能跑**：Node、依赖、网络这些先别跳过，先让 `openclaw` 本体成功启动。
2. **先做一个小任务验通路**：比如让它在仓库里新建一个 markdown 文件并写几行内容，再让它读出来核对。
3. **再加一层真实动作**：例如 git add + commit，确认它不只是“会说”，而是真的能“落地”。
4. **最后再碰外部能力**：像浏览器接管、消息通知、定时任务这类，放在基础稳定之后再接。

这一套下来，我的经验是：只要你能连续完成“写文件 → 读文件 → 执行命令 → 产出可验证结果”，基本就算上手成功了。

下面说几个我自己反复踩到的坑，先记住能少走弯路：

- **坑 1：工作目录搞错。** 你以为在 A 仓库改，实际跑在 B 目录，最后“改了个寂寞”。每次操作前先确认当前目录和目标路径。
- **坑 2：一次给太大目标。** 一上来就要“完整教程 + 全自动发布”，失败率很高。拆成小步，先拿到第一版可用结果。
- **坑 3：有写入没校验。** 文件写了不代表写对，命令跑了不代表成功。一定要做回读、看日志、查退出码。
- **坑 4：git 推送权限没提前配。** 本地提交没问题，推送时才发现 key 不对。像我这边就会固定用指定 SSH key，避免临场翻车。

接下来我会继续增量补这篇：下一版准备写 `openclaw` 在“博客维护”这个具体场景里的实战流程，包括我现在常用的任务模板、如何让它少犯错、以及我自己的一套检查清单。先把路走通，再谈优雅，效率会高很多。
