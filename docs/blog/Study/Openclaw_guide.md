## 第一部分：openclaw 是什么

openclaw 说白了，就是一个跑在服务器上的 agent 框架。它最让我眼前一亮的一点，是可以接到多个聊天平台里使用（比如 Discord、Telegram 这类），这样你在手机上就能直接“发消息调度它干活”，交互成本非常低。

我自己上手之后，能明显感受到它不是那种只会聊天的壳子，而是一个“能实际执行任务”的工作流入口。包括但不限于：

- 信息抓取（支持浏览器操作，包含登录态场景）
- coding（写代码、改代码、跑命令、排查问题）
- writing（整理文档、写博客、做结构化输出）
- scheduling（任务编排、分步执行、持续迭代）

说个很主观但真实的感受：第一次把 codex 放在 openclaw 这套命令行原生链路里跑起来时，体验和我在 Cursor 里用模型是两种感觉。

官方文档：

- <https://docs.openclaw.ai>
- <https://github.com/openclaw/openclaw>

## 第二部分：怎么安装

这一部分我自己的建议很简单：先别急着抄命令，先去官方文档把配置视频完整看一遍。这个投入看起来慢，但实际上会让后面少走很多弯路。

另外一个很实用的经验是：权限一定要做隔离，别一上来就把 openclaw 直接跑在 root 权限下。日常安装和运行尽量放在普通用户目录里，能满足需求就别提权。这样即使某一步操作失误，影响范围也会小很多，排查起来也更可控。

有个点对我启发很大：可以用 Tailscale 把机器和设备拉到同一个私有网络里，这样做远程访问和调试会顺很多。这个软件我以前只是“偶尔拿来用”，这次配 openclaw 才发现它真的很适合这类场景。

简单说一下 Tailscale：它是一个基于 WireGuard 的组网工具，能让不同设备像在同一局域网一样互联，省掉很多复杂的公网暴露和端口转发配置。

Tailscale 官网：<https://tailscale.com/>

最大的发挥 AI 能力的方式，还是“用 AI 配置 AI”。目前我自己的工作流是：本地 Mac 上用 codex 负责高频交互和改动，远端服务器上跑 openclaw 负责执行、联动和持续工作。两边配合起来，比单点工具更顺手。

### 2.1 我现在比较稳的一套：先有服务器，再让本地 codex 通过 SSH 接上

这个顺序我建议别反。先把服务器基础环境打稳（用户权限、Node、Python、网络、磁盘、日志目录），再在本地 codex 里配 SSH。原因很现实：一旦服务端基础不稳，你会把大量时间浪费在“到底是模型问题、网路问题、还是机器问题”的互相甩锅里。

我自己的做法是：

- 服务端先建普通用户，目录隔离，不直接拿 root 跑常驻进程。
- 先手工跑通 openclaw 基础命令，再接聊天平台，不要一步到位。
- 本地 codex 用 SSH 连上去后，优先把“看日志、重启服务、查配置”这三件事做成固定动作。

这一步其实决定了后续排障效率。我的体感是：SSH 链路越稳定，后面越不容易心态爆炸。

### 2.2 代理配置：全局代理和 Discord 专用代理要分开

这块我一开始就踩坑了。后面总结出来就是一句话：**全局代理负责基础出网，Discord 代理按通道单独配，不要混成一坨。**

#### 2.2.1 systemd 用户服务里配全局代理

在 `openclaw-gateway.service`（用户级 systemd）里，给网关进程加上环境变量：

- `HTTP_PROXY`
- `HTTPS_PROXY`
- `ALL_PROXY`

这样做的好处是：网关层面的联网请求有统一出口，不会今天走这个代理、明天走另一个代理。

#### 2.2.2 openclaw.json 里给 Discord 单独配代理

如果你 Discord 链路有单独要求（比如节点、协议、稳定性策略不同），就在 `openclaw.json` 里单独加：

- `channels.discord.proxy`

这能把“平台通道问题”和“系统全局出网问题”拆开。后面哪怕 Discord 抽风，也不影响你判断其他工具链是不是正常。

#### 2.2.3 修改配置后一定重启 gateway

这个我吃过亏：改完配置不重启，表面看“文件改了”，实际进程还在吃旧配置。我的固定动作是：改完 -> 重启 `openclaw-gateway` -> 立刻看日志确认新配置已生效。

### 2.3 Discord 接入

Discord 这块建议直接按官方步骤做，不要自己脑补流程。官方文档入口：

- OpenClaw 官方文档：<https://docs.openclaw.ai>

另外我会配合看一些中文经验帖做对照，尤其是首轮接入时少走弯路：

- 知乎参考（检索页）：<https://www.zhihu.com/search?type=content&q=OpenClaw%20Discord%20接入>

### 2.4 无头浏览器能力（Chrome + headless）

openclaw 的浏览器能力我觉得是很实用的一块，尤其是登录态、表单、后台页面这种传统 API 不好覆盖的场景。

我的建议是：

- 先确认 Chrome 可用（或对应运行时依赖齐全）。
- 默认按 headless 跑，先看稳定性和日志，再决定要不要可视化调试。
- 用 `browser status` / `browser start` 先做最小验证，确认“能启动、能连通、能执行动作”。

这一段别贪快，先把最小闭环跑通，再上复杂页面自动化，成功率会高很多。

## 第三部分：具体应用（目前研究出来的）

### 3.1 两次“玩坏”的经历（真实踩坑版）

我至少有两次把环境直接玩坏，核心问题都不是 openclaw 本身，而是我自己“改太猛、改太快”。

第一次是代理和通道配置混着改，改完没做最小验证，最后出现“看起来都通、实际都不稳定”的状态。第二次是模型和 token 一起动，结果问题叠加，排障难度直接翻倍。

现在回看，真正的问题是：没有控制变量。

### 3.2 为什么不要让 openclaw 频繁 restart gateway

频繁重启 gateway 在体感上像“快速刷新状态”，但实际很容易带来连锁副作用：

- 会打断正在跑的任务链路。
- 日志被切得很碎，定位问题更难。
- 某些平台连接反复重建，反而触发限流或异常状态。

我现在的策略是：除非确认是配置生效或进程异常，不要把 restart 当日常操作。先看日志、先定位，再决定要不要重启。

### 3.3 openrouter / API token + 默认模型改动引发的问题

这个是我自己的血泪教训：

- token 权限没收敛，或者调用链路没限制，真的会出现“token 烧得很快”的情况。
- 默认模型如果随手改成不稳定或不匹配的模型（比如我试过改到 `glm-5`），可能直接出现长时间卡死、响应异常慢、任务堆住不动。

所以我现在会把“模型可用性”和“token 消耗边界”当成上线前检查项，不再当临时小设置。

### 3.4 遇到 SSH 异常登录攻击后的教训

只要服务器暴露在公网，这个问题迟早会遇到。我碰到异常登录扫描后，最大的感受是：**安全不是锦上添花，是基础设施。**

后面我做的动作包括：

- 严控 SSH 登录方式，优先密钥登录，关闭弱口令路径。
- 日志定期看，不要等出事才翻。
- 把服务权限和系统权限拆开，避免单点失守后全盘失守。

### 3.5 出问题时，尽量让本地 codex 代理你排障

这条建议非常实战：当环境开始复杂、日志变多、人脑负荷上来时，让本地 codex 通过 SSH 代理你排障，效率通常比手动来回切窗口高很多。

我现在会让它先做三件事：

1. 汇总最近日志和错误时间线。
2. 列出可疑配置变更点。
3. 给出“最小回滚方案 + 验证步骤”。

这样你不会一慌就乱改，排障会稳得多。

### 3.6 安全提醒（建议每次改配置前看一眼）

这一节我想单独强调，尤其是刚开始折腾的时候很容易忽略：

- **最小权限原则**：能用普通用户就别用 root，能给只读就别给读写。
- **密钥边界**：不同用途的 key 分开，不要一把钥匙开所有门；泄露风险和审计难度会低很多。
- **模型权限边界**：高成本模型、外部 API、敏感工具调用要分层控制，别默认全开。
- **配置变更留痕**：每次改代理、模型、token，都要有记录，出问题时才能快速回溯。

说到底，openclaw 很强，但强工具要配强约束。把边界划清楚，才是真的长期可用。
